**Source**: red-team (BLOCKING), codex (BLOCKING #2), testability (#9), self-assessment
**Category**: security / trust-boundary (TB-006/TB-007) — AP-022 replay
**Description**: The "Overall readiness_verdict × entry_integrity (post-entry, closed table)" (spec ~664–672) designates `entry_integrity=unavailable → src/ ban still-lifted (monotonic) + verdict neutral/degraded` (non-failing). A commit-access actor (within INV-025's model) opens an activation PR that sets `lifecycle:BLOCKED→ENTERED` + `entry_evidence_pointer` and commits a bundle **crafted to make cosign FAULT** (a malformed Sigstore payload → panic/timeout — the CVE-2026-39395 class the pin floor exists for). `entry_integrity=unavailable`; because `effective_lifecycle` tracks the *declared* latch, `declared:ENTERED` lifts the src/ ban; because the fault is `unavailable` (not `rejected`), the table yields a **non-failing verdict** → the bogus activation merges and a following PR lands `src/` on an unproven baseline. INV-029's "activation acceptance requires a *verifying* entry receipt" lives only in prose, NOT as a table dimension — the exact AP-022 shape (a "closed" table whose safety depends on an unrepresented dimension, failing open on the accept side). **Fix**: make `is_activation_event` an explicit dimension; `(activation-event, unavailable|rejected|absent) → hard-red / fail-closed`; enforce with a cross-product test over `transition_state × entry_integrity × declared_lifecycle` asserting no first-activation without `verified` ever yields a non-failing verdict.
**Status**: accepted — incorporated 2026-07-27

## Finding RS-002: INV-012 default direction is fail-open — an unclassified cosign fault must map to `rejected`, not `unavailable`
**Source**: red-team (HIGH), codex (#12 HIGH)
**Category**: security — fail-open default (AP-001) + non-total mapping (AP-022)
**Description**: INV-012 maps "verifier/tool faults → `unavailable`; policy/crypto/staleness/ancestry → `rejected`," but the DEFAULT direction for an *unclassifiable* cosign outcome (panic, SIGSEGV, unknown non-zero exit, timeout) is unpinned and would fall into the broad `unavailable` bucket. Because `unavailable` is non-failing in both the entry-integrity context (arms RS-001) and the post-entry health context (`p3-verifier-unavailable` = neutral), any crafted-fault input fails open. Separately, `trust-root-or-pin-mismatch` conflates a transient absent/unreadable tool (→ unavailable) with a digest/root MISMATCH (→ must be rejected/hard-red) in one reason class, so the "total" mapping isn't total over the underlying observations. **Fix**: reserve `unavailable` for a closed, positively-enumerated set (binary-absent, provisioning-not-completed, trust-root-file-unreadable); map every other/unknown/crash/signal/timeout to `rejected` (fail-closed); split absent-tooling from digest/root-mismatch; pin the DEFAULT branch to `rejected` and cross-product-test against a committed cosign-exit-code enum.
**Status**: accepted — incorporated 2026-07-27

## Finding RS-003: Pre-ENTERED P3-refresh deadlock — no allowlist mode can legally restore P3 before entry (AP-021 circular gate)
**Source**: codex (BLOCKING #1)
**Category**: correctness / lifecycle — non-bootstrappable gate (AP-021)
**Description**: After PR3 (`P3.satisfied:true`, `lifecycle:BLOCKED`, P2 still false), a PR changes a determinism-relevant file → its manifest is stale → the real P3 probe returns false while the declared block still says `satisfied:true` (a declared-vs-actual mismatch the gate rejects). The PR cannot obtain a fresh signature (signing is main-push-only). Flipping P3 false to unblock is illegal: PRH-004 says only PR3 may set P3 true, and the P3-**refresh** mode (INV-028/PRH-007) is **post-entry only** and forbids changing the flag. So once P3 is staled pre-entry, **P3 can never be restored → phase entry deadlocks** — the AP-021 circular-gate class the project has been bitten by twice. **Fix**: define a pre-entry `invalidate → merge → main-sign → reactivate` protocol and a corresponding 4th PRH-007 allowlist mode that can legally re-mint/restore P3 while `lifecycle=BLOCKED`.
**Status**: accepted — incorporated 2026-07-27

## Finding RS-005: `comparison_status=equal` never cross-checks the recorded projection-policy identity against the manifest-pinned policy — a no-op projection mints P3
**Source**: codex (BLOCKING #3)
**Category**: security / data-integrity (INV-002/006/012)
**Description**: A producer emits all ten required role records but applies an **empty/unrecognized projection** to each, recording identical projection hashes while raw artifacts differ. INV-002 derives `equal` from role/kind completeness + registry set-equality + per-role projection *hash* equality, but never asserts that each recorded per-role projection *policy identity* (schema/version/digest) equals the pinned policy for that role/kind. The minimal signer schema-checks this internally-consistent receipt; the gate reconstructs the same receipt-backed Statement → **P3 true without measuring the declared projections**. **Mitigation to assess (why this may be less than fully blocking):** INV-018 lists the projection code digest in the manifest and INV-006 binds the manifest digest into the signed receipt, and INV-019 requires the manifest non-stale on HEAD — so if the producer is *forced* to run the manifest-pinned projection code, a no-op projection changes the code digest → stale → rejected. The gap is that the spec never requires the receipt's *recorded* projection identity to equal the *manifest's* projection identity, so the closure relies on an unstated "producer runs exactly the pinned code" assumption. **Fix**: add a closed role/kind→projection-policy map; require exact policy version/digest equality (recorded == manifest-pinned) before aggregate equality/signing/verification; preferably have the signer re-derive projections from producer artifacts.
**Status**: accepted — incorporated 2026-07-27
